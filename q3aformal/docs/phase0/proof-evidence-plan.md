# Phase 0 Proof Evidence and Checker Plan

**Status:** Gate A evaluation completed. The owner selected Deletion Resolution Asymmetric Tautology (DRAT) at Gate B on 2026-11-24.  
**Scope:** Phase 0 proof and checker plan. The [Gate B decision package](../../evidence/phase0-go-no-go.md) records the accepted proof evidence and Phase 1 decision.

## Proof demonstration

The known-pass run must establish an unbounded property. Use a one-inductive property or a complete inductive invariant. The evidence must cover both:
1. the required initial/base obligation; and
2. the inductive-step obligation under the same assumptions and exact transition model.

Finite bounded model checking with no counterexample is BOUNDED_PASS and cannot satisfy the PROVEN demonstration.

The known-fail run is a separate job. Its candidate witness is checked frame by frame against the exact transition relation and assumptions. Only a validated witness may produce FAIL.

## DRAT evaluation candidate

Evaluate DRAT for the SAT unsatisfiability obligations generated by the induction base/step. Keep the proof search implementation separate from the checker. The checker verifies the proof against the exact canonical query and rejects:
- an invalid or incomplete proof;
- a proof for a different query/model hash;
- malformed syntax or identifiers outside the artifact schema;
- inconsistent metadata, schema, or checker version.

The prototype may retain a minimal checker architecture, but the final proof format is not frozen until checker size, validation corpus, portability, and performance evidence are reviewed.

## Checker acceptance corpus

Create independently authored artifacts for each supported obligation:

- Valid proof artifacts that must be accepted.
- Artifacts with one deliberately altered literal/clause or missing proof step that must be rejected.
- Malformed artifacts that must return a diagnostic and must never pass.
- Valid witness, invalid transition, violated-assumption, and non-failing witness cases.
- Model/query hash mismatch and unsupported schema cases.

Expected outcomes are reviewed independently of the checker implementation. No third-party formal engine, solver, or proof checker is used as an acceptance oracle.

## Revalidation and bundle identity

Every proof report records the Q3A build, checker fingerprint, artifact schema, exact T-IR hash, property/query hash, assumptions, and reset policy. A compatible checker revalidates the stored evidence before a result is represented as current. Without a compatible checker, the result is labeled historical.
